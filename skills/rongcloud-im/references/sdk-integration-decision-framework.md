# SDK 集成决策框架

本文定义融云 IM 集成的五层决策流程，用于系统评估实现路径，并以满足需求的最优方式实现。

## 决策流程概览

编写集成代码前，先记录用户是否指定 SDK，再选择入口：

- 用户未指定 SDK：从第 1 层开始，只有上一层无法满足需求时才进入下一层。
- 用户明确选择 IMKit：将 IMKit 记录为约束，从第 1 层开始；第 1、2 层均无法满足时，先说明限制并获得用户同意，才能进入 IMLib 第 3 层。
- 用户明确选择 IMLib：将 IMLib 记录为约束，跳过第 1、2 层，直接进入第 3 层；不得仅因 IMKit 更省开发成本而改变用户选择。

在 IMLib 约束下，如果第 3 层无法满足需求，先说明 IMLib 的限制以及继续采用 IMLib 的替代方案。只有确实需要改用 IMKit 时，才说明切换原因、能力差异和维护影响，并获得用户明确同意；同意后再评估相关 IMKit 层级，未同意则保持 IMLib 约束。

## 第 1 层：评估 IMKit 原生能力

目标是优先采用成本最低、开箱即用的方案。检查能力前，先按 [功能清单使用规则](./feature-lists.md) 确认功能在目标平台 IMKit 的覆盖情况和首次支持版本，再验证项目 SDK 版本是否满足。检查 IMKit 文档是否已有满足需求的界面、API、组件或配置，并确认目标平台可用。若满足，直接集成；否则进入第 2 层。

## 第 2 层：评估 IMKit 定制与扩展能力

IMKit 没有直接功能时，先检查是否能通过扩展点间接实现，而不是立即降级到 SDK。常见扩展包括自定义视图/组件、事件回调和生命周期 hook、主题和样式覆盖、配置项和功能开关、slot 与 render props。若扩展点可满足需求，继续留在 IMKit 生态中；否则进入第 3 层。

## 第 3 层：评估 IMLib API 层

在未指定 SDK 或用户同意从 IMKit 切换时，本层承接前两层；用户明确选择 IMLib 时，本层是直接入口。检查能力前，先按 [功能清单使用规则](./feature-lists.md) 确认功能在目标平台 IMLib 的支持情况和首次支持版本，再验证项目 SDK 版本是否满足。检查底层 IMLib 是否提供低层能力，可以直接调用 SDK API、构建自定义 UI，或与现有 IMKit 组件组合。实现时明确标注这是 IMLib 实现或补充实现，便于维护；在允许继续进入后续层级的前提下，若仍不满足再进入第 4 层。

## 第 4 层：评估修改源代码

如果 SDK 也没有官方接口，并且当前方案使用 IMKit，评估修改 IMKit 源代码的可行性：技术可行性、影响范围、升级维护成本以及稳定性/安全风险。用户明确选择 IMLib 且尚未同意切换到 IMKit 时，不进入本层。

执行步骤：

1. 评估技术可行性和风险。
2. 向用户说明为何前三层无法满足、具体修改点、影响范围、维护成本和升级风险。
3. 明确询问用户是否接受修改源代码。
4. 在用户明确回复前暂停，不得直接修改源代码。

## 第 5 层：最终决策

### 分支 A：用户批准修改源代码

从 [IMKit 源码仓库](./imkit-repositories.md) 获取目标平台源码，在本地或团队 Fork 中开发、测试并实现。交付变更说明，包括修改文件和位置、每项变更原因与逻辑，以及未来版本升级注意事项。

### 分支 B：用户不批准修改源代码

寻找不改源码的替代方案：调整产品设计、使用应用层包装模拟相近结果，或探索原生平台能力/WebView 注入。说明权衡和限制，获得同意后再实现。

### 分支 C：没有可行方案

按 [功能清单使用规则](./feature-lists.md) 验证后，明确告知当前 SDK 版本无法实现,说明技术限制,并建议访问 [融云官网](https://www.rongcloud.cn/)、调整需求以使用现有能力,或等待未来 SDK 版本。

## 使用建议

除用户明确选择 IMLib 时从第 3 层开始外，不跳过层级。记录用户的 SDK 约束、已评估的层级、前面层级为何不足、最终采用的层级，以及第 3/4 层方案的维护事项。稳定性和可维护性优先，源码修改只能作为最后手段；任何 SDK 切换、源码修改或替代方案都必须透明说明并获得批准。
